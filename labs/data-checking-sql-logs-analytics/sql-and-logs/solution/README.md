# 해설 — SQL과 로그로 데이터 정합성 결함 찾기

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 이 폴더의 `q*.sql`은 모범 답안이고, 같은 결과를 내는 다른 쿼리도 정답입니다.

## t1 — 직접 확인하기
- 세 쿼리 모두 **취소·환불을 뺄지**가 핵심 규칙이었습니다. `q1`(상태별 주문 수)은 전체를 세고, `q2`·`q3`(매출·구매액)는 `status IN ('PAID','SHIPPED','DELIVERED')`로 거릅니다. 같은 `orders` 테이블이라도 질문에 따라 "무엇을 센다"가 달라집니다.
- 월 경계(`to_char(created_at, 'YYYY-MM')`)는 `created_at`이 시간대 없는 한국 시각이기 때문에 안전합니다. `timestamptz`였다면 세션 시간대에 따라 월말·월초 주문의 월이 달라졌을 것입니다.

## t2 — 정합성 쿼리
| 쿼리 | 기법 | 흔한 실수 |
|---|---|---|
| 고아 품목 | `LEFT JOIN … WHERE o.id IS NULL` (또는 `NOT EXISTS`) | `INNER JOIN`으로는 짝 없는 행이 사라진다 |
| 중복 주문 | 자기 자신과 `EXISTS` 비교: 같은 회원·금액, 더 작은 `id`, 시각 차이 10초 이하 | `GROUP BY member_id, total_amount HAVING COUNT(*)>1`은 **다른 날의 같은 금액 주문**까지 중복으로 잡고, 원본과 복사본을 **모두** 돌려준다 (지울 것은 나중 주문 하나) |
| 합계 불일치 | 품목을 주문별로 먼저 합산한 서브쿼리와 `JOIN` 후 공식 비교 | 품목을 `JOIN`한 채로 `SUM`하면 `grade_discount` 등이 품목 수만큼 중복되어 더해진다 |
| 중복 회원 | `lower(trim(email))`로 정규화한 값 비교 | `GROUP BY email`은 대소문자·공백이 다르면 같은 이메일로 보지 않는다 → **0행**이 나와 "중복 없음"으로 오해하기 쉽다 |

합계 불일치 8건은 두 종류입니다. **쿠폰 할인이 합계에서 빠진 5건**(차이가 3,000원 또는 5,000원)과 **등급 할인이 1원 올림되어 저장된 3건**(차이 1원)입니다. 1원 차이는 합계가 "대충 맞아 보여서" 눈으로는 절대 찾지 못합니다. 이것이 이 랩에서 공식 전체를 쿼리로 확인하는 이유입니다.

## t3 — 로그 읽기
- 5xx 37건 중 35건은 결제(`POST /api/orders/:id/pay`)이고 2건은 **결제와 무관한 교착(deadlock) 500**입니다. 그래서 "첫 5xx"(13:02)와 "마지막 5xx"(15:21)는 **장애 시간대(14:10~14:32)와 다릅니다.** 5xx 전체의 첫·마지막과 "장애의 시작·끝"은 다른 질문입니다.
- 엔드포인트를 센다면 `/api/orders/812/pay`와 `/api/orders/813/pay`를 같은 것으로 묶어야 합니다(`:id`로 정규화). 묶지 않으면 한 엔드포인트당 1~2건으로 흩어져 "가장 많은 엔드포인트"가 보이지 않습니다.

## t4 — 상관 ID
- 같은 주문 842에 결제 요청이 두 번 있습니다. 14시대의 **502 실패**, 그리고 장애가 끝난 14:41의 **200 성공**. 고객 문의는 "안 됩니다"였으므로 실패한 요청을 골라야 하고, 두 요청의 요청 ID는 다릅니다.
- `access.log`의 `rid=`와 `app.log`의 `reqId`가 같은 값이라서 두 로그를 연결할 수 있습니다. access.log는 "무슨 요청이 몇 시에 어떤 상태로 끝났나"를, app.log는 "그 요청 안에서 무슨 일이 있었나"(게이트웨이 3회 시도, 모두 타임아웃)를 알려 줍니다.
- 결함 리포트에 이 증거를 쓰면 개발자가 로그 한 번으로 재현 없이도 원인(게이트웨이 타임아웃)에 접근할 수 있습니다.
