# 해설 — Swagger UI·mitmproxy·패킷 캡처

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 이 폴더에 모범 답안 파일(`t1-scenario.yaml`, `api.collection.json`, `addon.py`, `t4-answers.yaml`)이 있습니다.

## t1 — Swagger UI
- Authorize는 `bearerAuth`에 **토큰만** 넣습니다. 한 번 넣으면 열려 있는 모든 오퍼레이션의 요청에 붙고, 사용자를 바꾸려면 다시 Authorize 합니다.
- 질문은 도구의 기능을 하나씩 쓰게 합니다: 인증(q1·q2), 목록 응답 훑기(q3), 요청 본문 편집(q4), 인증 없이 호출(q5), 일부러 잘못된 입력(q6).
- 오류 응답의 `code`는 서버가 약속한 오류 종류입니다. 상태 코드(숫자)와 다릅니다. 둘 다 계약이지만 클라이언트가 분기하는 것은 보통 `code`입니다.

## t2 — 파이프라인
- 변환기의 산출물은 **뼈대**입니다. 요청 본문은 스키마의 예시 값(`<string>`)이고, 인증은 변수 참조(`{{bearerToken}}`)만 있습니다. 변수를 채우는 책임은 사람(또는 로그인 요청의 Tests)에 있습니다.
- 변환기는 오퍼레이션을 **태그별 폴더**로 묶습니다. 폴더 순서가 곧 실행 순서라 로그인이 뒤에 있으면 그 앞의 인증 요청은 `401`을 받습니다. 모범 답안은 로그인 요청을 맨 앞으로 옮겼습니다.
- 컬렉션 맨 위(`event`의 `test`)에 쓴 스크립트는 **모든 요청 뒤에** 실행됩니다. 모범 답안은 "서버 오류(5xx)가 아니다"를 한 번만 썼고, 이것이 요청 수만큼 검증으로 센 이유입니다. 요청마다 의미 있는 검증을 더 쓰면 더 좋은 컬렉션이 됩니다(앞 랩 t1).
- 명세가 바뀌면 같은 명령으로 컬렉션을 다시 만들 수 있습니다. 다시 만들 때 손으로 고친 부분이 사라지므로, 실무에서는 고치는 부분을 스크립트로 자동화하거나 변환 결과 위에 얹는 별도 컬렉션을 둡니다.

## t3 — mitmproxy
| 하고 싶은 일 | 훅 | 핵심 |
|---|---|---|
| 요청 헤더 바꾸기 | `request` | `flow.request.headers[...] = ...` (대입이므로 덮어쓰기) |
| 서버에 보내지 않고 답하기 | `request` | `flow.response`를 채우면 요청은 전달되지 않는다 |
| 모든 응답에 공통 처리 | `response` | 직접 만든 응답에도 불린다 → 헤더·카운터를 한 곳에 |
| 요청 수 세기 | 애드온 객체 | `__init__`의 속성 (프로세스가 사는 동안 유지) |

- 경로 비교는 정규식으로 하고 쿼리는 떼고 비교합니다(`path.split("?")[0]`).
- 가로챈 결제 요청이 앱에 닿지 않았다는 것은 **앱을 직접 조회해서** 확인합니다. 프록시가 하는 말을 프록시로 확인하면 증거가 되지 않습니다.
- 요청 변조로 결함을 켜는 방식은, 코드를 고치지 않고 특정 요청에만 결함을 재현할 때 유용합니다.

## t4 — 패킷 캡처
| 질문 | 도구 |
|---|---|
| 평문 비밀번호 | 로그인 요청 패킷 내용. HTTP 가 아니라 HTTPS 였다면 보이지 않았을 정보입니다 |
| 토큰 앞 8글자 | `Authorization` 헤더. 토큰도 평문이면 가로채서 재사용할 수 있습니다 |
| 서버 오류 경로 | `http.response.code >= 500`에서 응답 패킷 → 짝이 되는 요청 |
| 가장 느린 요청 | `http.time`. 요청이 재전송되었다면 **처음** 보낸 패킷부터 잽니다 |
| 재전송 | `tcp.analysis.retransmission` |

- 느린 응답과 요청 재전송은 같은 요청에서 함께 나타났습니다. 네트워크 문제인지 서버 처리 지연인지 가르려면 서버가 요청을 받았다는 ACK 가 언제 왔는지를 봐야 합니다.
- 이 캡처는 합성 데이터입니다. 실제 서비스에서는 HTTPS 라 내용이 암호화되어 있고, 이런 분석은 TLS 복호화 키가 있을 때 가능합니다.
