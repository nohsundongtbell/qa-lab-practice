# 해설 — QA 숍 API 계약 점검

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 숨은 결함이 정확히 무엇인지는 적지 않고, 어떤 *종류*의 검증이 어떤 종류의 위반을 잡는지까지만 씁니다.

이 폴더의 `collection.json`과 `tests/t2-contract.test.mjs`가 모범 답안입니다. `npm run solution -- api-contract-testing/shop-api-contract --yes`가 안내하는 위치에서 열어 보세요.

## t1 — 컬렉션
- **요청은 흐름으로 짠다**: 로그인 → 토큰 저장(`pm.collectionVariables.set`) → 이후 요청에 `{{token}}`. 주문은 장바구니를 채우고 만든 뒤 `id`를 저장해 조회·결제·취소에 씁니다.
- **응답마다 세 가지를 본다**
  | 종류 | 예 |
  |---|---|
  | 필수 필드 | `for (const k of [...]) pm.expect(m).to.have.property(k)` |
  | 타입 | `Number.isInteger(price)`, 문자열이 아닌지 |
  | 열거값 | `pm.expect([...]).to.include(order.status)` |
- **오류 응답도 계약이다**: 모든 오류 응답은 `code`·`message`·`details`를 가집니다. 이 검증을 오류 요청마다 붙이면 한 군데서 빠진 필드도 잡힙니다.
- **정확한 상태 코드**: "400이어야 하는 곳에서 5xx를 돌려주는가"는 `to.have.status(400)`으로만 잡힙니다. `to.be.below(500)` 같은 느슨한 확인은 놓칩니다.
- 같은 데이터를 돌려주는 API(목록·상세, 생성·조회)를 **각각** 검증해야 합니다. 한쪽만 틀린 경우가 있습니다.

## t2 — 명세 대조
- 도구는 명세의 응답 스키마를 Ajv로 컴파일해 응답 본문을 검증하고, **명세에 없는 상태 코드**도 위반으로 봅니다.
- 그래서 t1처럼 필드를 하나씩 쓰지 않아도 됩니다. 대신 **무엇을 호출하느냐**가 전부입니다: 정상 응답뿐 아니라 오류가 나는 입력(없는 자원, 잘못된 값, 토큰 없음)을 호출해야 오류 응답 쪽 위반이 드러납니다.
- `contract()` 같은 작은 도우미로 "기대 상태 코드 확인 → 명세 대조"를 묶으면 테스트가 짧아집니다.
- 한계: 스키마 대조는 **값이 맞는지**(예: 주문 상태가 실제로 `PENDING`인지)는 모릅니다. 값은 `expect`로 따로 확인해야 합니다. 계약 테스트와 기능 테스트는 서로 대체하지 못합니다.

## t3 — 커버리지
- 오퍼레이션 커버리지는 "호출했는가", 상태 코드 커버리지는 "그 오퍼레이션이 약속한 응답을 실제로 받아 봤는가"입니다. 앞의 것만 높으면 정상 경로만 도는 컬렉션이 됩니다.
- 오류 상태 코드를 받으려면 일부러 실패를 만들어야 합니다: 토큰 없이(`401`), 남의 자원(`404`), 일반 회원이 관리자 API(`403`), 상태가 맞지 않는 동작(`409`), 두 사용자가 마지막 재고를 다툼(`409`), 승인 거절 카드(`402`).
- 순서 의존이 있는 흐름은 변수를 저장해 이어 가고, **파괴적인 요청은 마지막에** 두세요(환불 이후에는 같은 주문으로 다른 것을 시험할 수 없습니다).
- 커버리지 100%는 "결함이 없다"가 아니라 "명세가 약속한 모든 응답을 한 번은 봤다"는 뜻입니다.
