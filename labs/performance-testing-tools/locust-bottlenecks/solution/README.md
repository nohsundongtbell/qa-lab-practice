# 해설 — Locust 부하 시나리오와 병목 찾기

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 이 폴더의 `locustfile.py`와 `result.yaml`이 모범 답안입니다.

## t1 — 시나리오 설계
- **사용자 단위로 생각한다**: `HttpUser` 한 인스턴스가 실제 사용자 한 명입니다. 로그인은 `on_start`에서 한 번, 토큰은 세션 헤더에 넣어 이후 모든 요청에 자동으로 붙입니다. 요청마다 로그인하면 로그인 API가 부하의 대부분을 차지해 측정이 왜곡됩니다.
- **가중치(`@task(n)`)는 실제 행동 비율**: 상품 보기가 주문 보기보다 훨씬 잦다면 그렇게 씁니다. 모든 요청을 같은 빈도로 보내면 현실과 다른 부하입니다.
- **생각 시간(`wait_time`)**: 사람은 요청 사이에 멈춥니다. 0으로 두면 "동시 사용자 10명"이 아니라 쉬지 않는 요청 폭탄이 됩니다.
- **준비는 시작 때 한 번**: 주문 8건은 `test_start`에서 만듭니다. 사용자 10명이 각자 만들면 데이터 양이 사용자 수에 따라 달라져 결과를 비교할 수 없습니다.
- **측정 대상과 준비 코드를 분리**: 준비용 호출(fixture)은 Locust의 통계에 잡히지 않는 일반 `requests`로 했습니다.

## t2 — 병목 찾기
| 엔드포인트 | 결함 없음 | 결함을 켰을 때 | 읽는 법 |
|---|---|---|---|
| `GET /api/products` | 수십 ms | 수백 ms | 요청마다 일정하게 느림 → 한 번의 요청도 이미 느리다 |
| `POST /api/quote` | 수십 ms | 같음 | 병목이 아님. 목표 안 |
| `GET /api/orders` | 수십 ms | 주문 수에 비례해 느려짐 | 주문 8건이면 건당 지연이 쌓임 (N+1 의심) |

- **평균 말고 p95**: 평균은 빠른 요청에 희석됩니다. 사용자 10명 중 한 명이 늘 느리게 겪는 값이 p95입니다.
- **비교 실험의 원칙**: 시나리오·사용자 수·시간·데이터는 고정하고 **결함 하나만** 바꿉니다. 그래야 변화의 원인이 그 결함이라고 말할 수 있습니다.
- 상품 목록 결함은 응답이 느릴 뿐 아니라 **데이터베이스 연결을 붙잡고 기다립니다.** 동시 사용자가 늘면 연결이 모자라 다른 요청까지 줄 서게 됩니다(대기열). 단일 요청 시험(`max_ms`)에서는 "느림"만 보이고, 부하 시험에서는 "다른 요청까지 느려지는 정도"가 보입니다. 두 시험은 서로 다른 것을 알려 줍니다.
- 한계: 이 랩은 내 컴퓨터 안에서 앱과 부하 도구가 자원을 나눠 씁니다. 숫자의 절댓값이 아니라 **결함 유무에 따른 차이**를 믿으세요.
