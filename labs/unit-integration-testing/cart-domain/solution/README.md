# 해설 — 장바구니 도메인 단위·통합 테스트

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 뮤턴트가 정확히 어떻게 고장 났는지는 적지 않습니다 — 아래 "테스트가 무엇을 지켜 주는가"에서 짐작할 수 있는 수준까지만 씁니다.

## t1 — 순수 함수 단위 테스트
- **경계는 세 점**: 49,999 · 50,000 · 50,001. 같은 경계가 `>=`인지 `>`인지는 정확히 경계값에서만 드러납니다.
- **두 규칙이 겹치는 곳**: 도서산간 추가 운임은 무료 배송과 독립입니다. 겹치는 입력(50,000원 + 도서산간)이 필요합니다.
- **잘못된 입력**은 "예외가 난다"까지 검증해야 합니다. 음수와 소수는 서로 다른 검증이라 둘 다 필요합니다.
- **반올림 방향**은 49.9원처럼 소수가 나오는 금액이 아니면 드러나지 않습니다.
- `it.each`로 표를 쓰면 경계 케이스를 한눈에 읽을 수 있습니다.

## t2 — 테스트 더블
| 더블 | 이 풀이에서 | 용도 |
|---|---|---|
| 스텁 | `charge: vi.fn().mockResolvedValue({ approved: true, … })` | 협력자가 정해진 값을 돌려주게 해서 "승인/거절" 상황을 만든다 |
| 스파이·목 | `mailer.send`, `orders.save`, `gateway.charge` | 호출 여부·횟수·인자를 확인한다 |

- 반환값만 확인하면 "메일이 나갔는가", "저장했는가"를 놓칩니다. 부수 효과는 호출 기록으로 확인합니다.
- **하지 않아야 할 일**(`not.toHaveBeenCalled`)이 거절 경로의 핵심입니다.
- 결제 금액처럼 계산이 얽힌 값은 `toHaveBeenCalledWith`로 **정확한 객체**를 확인해야 합니다. `expect.objectContaining`은 관심 없는 필드를 건너뛸 때만 쓰세요.

## t3 — 플래키 테스트
시작 파일의 테스트는 `Date.now()`를 **두 번** 불러서(`issueVoucher` 안, 테스트 안) 두 값이 같아야 통과하는 구조입니다. 같은 밀리초 안에 끝나면 통과하고, 아니면 실패하니 "가끔" 실패합니다.

고치는 원칙은 하나입니다: **시계와 난수를 테스트의 입력으로 만든다.**
- `vi.useFakeTimers()` + `vi.setSystemTime()` → 지금이 언제인지 테스트가 정한다.
- `vi.spyOn(Math, 'random')` → 난수가 무엇인지 테스트가 정한다.
- 현지 시각을 쓰는 코드(`getHours`)는 **현지 시각 생성자**로 시각을 만들어야 시간대와 무관해집니다. `'…+09:00'`로 만들면 서울에서만 통과합니다.
- 코드를 바꿀 수 있다면 더 좋은 해법은 시계·난수를 인자로 **주입**받게 하는 것입니다(t2의 `newOrderId`처럼). 이 랩은 코드를 고치지 않고 테스트만으로 통제하는 방법을 연습합니다.

## 테스트가 무엇을 지켜 주는가 (뮤턴트의 종류)
| 뮤턴트가 건드린 곳 | 이를 잡는 테스트 |
|---|---|
| 경계 비교 연산자 | 경계 정확히 · 바로 아래 |
| 조건 결합(겹치는 규칙) | 두 규칙이 동시에 참인 입력 |
| 입력 검증 | `toThrow` |
| 반올림, 상수 | 소수가 나오는 입력, 모든 등급 값 |
| 호출 인자·횟수 | `toHaveBeenCalledWith` / `…Times` |
| 호출되지 않아야 할 경로 | `not.toHaveBeenCalled` |
| 시간·난수에 의존한 계산 | 가짜 시계, 난수 고정 |
