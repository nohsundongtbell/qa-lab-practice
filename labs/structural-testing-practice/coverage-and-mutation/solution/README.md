# 해설 — 커버리지와 뮤테이션

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 뮤턴트가 정확히 어떻게 고장 났는지는 적지 않습니다.

## t1 — 줄 커버리지 100%의 함정
시작 테스트는 줄 커버리지가 이미 100%였는데 분기 커버리지는 `coupon.mjs` 91.66%, `order-status.mjs` 50%였습니다.

- `if (x) return …` 처럼 **한 줄에 조건과 동작이 같이 있으면**, 조건이 거짓인 경우만 실행해도 그 줄은 "실행됨"으로 계산됩니다. 반대로 참인 경우만 실행해도 마찬가지입니다.
- 삼항 연산자 `a ? b : c`와 `&&`/`||`도 한 줄이라 줄 커버리지에는 거의 드러나지 않습니다. 분기 커버리지는 이런 곳을 따로 셉니다.
- 분기 100%를 채우려면 각 `if`의 참·거짓, 각 삼항의 두 갈래를 한 번씩 지나가면 됩니다.

## t2 — 커버리지 100%인데 살아남는 뮤턴트
"모든 분기를 지나가기만 하는" 테스트(두 파일에 테스트 2개)는 줄 100% · 분기 100%였지만 뮤턴트 11개 중 **7개가 살아남았습니다**. 어서션 없이 함수를 호출하기만 하는 테스트는 커버리지 100%에 처치 0개였습니다.

| 살아남은 종류 | 이유 | 처치하는 테스트 |
|---|---|---|
| 경계 비교(`<` ↔ `<=`, `>` ↔ `>=`) | 두 분기를 모두 지나갔어도 경계 **정확히 그 값**은 안 넣었다 | 바로 아래 · 정확히 · 바로 위 |
| 반올림 방향 | 나누어떨어지는 값만 썼다 | 소수가 나오는 입력 |
| 상한(`Math.min`) | 상한에 걸리는 입력을 안 썼다 | 할인액이 상품 금액보다 큰 입력 |
| 특수 값(0원) | 0은 "정상"인지 "오류"인지 확인하지 않았다 | 0 입력 |
| 조건의 다른 갈래(`VIP` 외 등급, `DELIVERED` 외 상태) | 한 가지 대표 값만 썼다 | 대표 값 외의 값들 |
| 계산 결과(`total - fee`) | 수수료가 0인 경우만 확인했다 | 수수료가 붙는 경우의 **환불액** |

처치하기 쉬운 뮤턴트(`easy`: 분기를 뒤집거나 상수·부호를 바꾼 것)는 커버리지를 채우는 테스트도 대개 처치합니다. 남는 것은 **경계와 특수 입력**에 숨은 뮤턴트(`subtle`)입니다.

## t3 — 정의-사용 쌍
- 순환 복잡도 = 판단 지점 3개(`weightKg > 10`, `express`, `else if remote`) + 1 = **4**. 독립적인 경로가 4개라는 뜻이고, 이 함수의 모든 분기를 덮는 데 필요한 테스트는 최소 3~4개입니다.
- `fee`의 정의는 D1, D3, D4이고, `days`의 정의는 D2, D5, D6입니다. **D3이나 D4가 실행되면 그 앞의 정의는 덮어써져서** 그 뒤의 사용에는 도달하지 못합니다. 그래서 D1-U1은 있어도 `D1-U4`는 "10kg 이하이고 특급이 아닌" 경로에서만 존재합니다.
- 흔한 실수: ① 정의와 사용 사이에 재정의가 끼어 있는데도 쌍으로 적는다(예: 다른 변수의 정의와 섞기) ② 도달 가능한 쌍을 놓친다(`D1-U2`처럼 앞의 `if`를 건너뛴 경로).
- 이 정답표는 6개 실행 경로를 모두 시뮬레이션한 결과와 같은지 테스트로 검증합니다(`check/analysis.test.mjs`).
