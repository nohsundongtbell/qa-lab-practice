# 해설 — QA 숍 화면 자동화

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 이 폴더의 `tests/`와 `pages/`가 모범 답안입니다.

## t1 — 구매 흐름
- 기대 금액은 사양서로 직접 계산합니다: 50,000원 × 2 = 100,000원, NORMAL 등급 할인 없음, 50,000원 이상이라 배송비 무료. **앱이 보여 주는 값을 복사해 기대값으로 쓰면** 앱이 틀려도 통과하는 테스트가 됩니다.
- 로그인 실패 테스트는 "메시지가 보인다"와 "로그인되지 않았다(내 이름이 없다)"를 **둘 다** 확인합니다. 부정 확인은 `toHaveCount(0)`처럼 웹 우선 단언으로 씁니다.

## t2 — 로케이터
| 시작 예시의 로케이터 | 왜 깨지는가 | 대신 |
|---|---|---|
| `form input` + `.nth(0)` | 필드 순서가 바뀜 | `getByLabel('이메일')` |
| `button.primary` | 클래스 이름이 바뀜 | `getByRole('button', { name: '로그인' })` |
| `.products .card:nth-child(1) button` | 컨테이너·클래스·순서가 바뀜 | `getByTestId('product-card').filter({ hasText })` 안의 `getByRole('button')` |

- v2는 보이는 글자·접근 가능한 이름·역할·`data-testid`를 바꾸지 않습니다. 사용자(그리고 보조 기술)가 보는 것이 같으면 테스트도 같아야 한다는 원칙입니다.
- 테스트마다 다른 회원을 쓴 이유: 한 테스트가 담은 장바구니가 다음 테스트의 금액을 바꾸기 때문입니다. 테스트 사이의 숨은 의존은 순서나 병렬 실행에서 터집니다.

## t3 — 안정성
- 시작 예시는 `waitForTimeout(500)`으로 로그인이 끝나기를 "바랍니다". 응답이 0.5초보다 오래 걸리는 날(unstable의 약 30%)에 실패합니다. 고정 대기는 느린 환경에서는 모자라고, 빠른 환경에서는 낭비입니다.
- 페이지를 새로 열면 앱은 회원 정보를 다시 읽어 옵니다. 그 전에 누른 "담기"는 로그인 화면으로 튕깁니다. 실제 사용자는 화면이 준비된 것을 **보고** 누르므로, 테스트도 같은 신호(내 이름, 상품 카드)를 기다립니다. 이 대기를 `ProductsPage.open()` 한 곳에 모으면 모든 테스트가 같은 보호를 받습니다.
- 페이지 객체의 가치는 "로케이터와 대기 규칙을 한곳에" 둔다는 데 있습니다. 화면이 바뀌면 페이지 객체만 고치면 됩니다. 검증(`expect`)은 보통 테스트 쪽에 두어 테스트가 무엇을 기대하는지 읽히게 합니다.
- 직접 재현: `LATENCY=unstable`로 같은 테스트를 10번 돌려 보면 불안정한 테스트가 드러납니다. 한 번 통과했다고 안정적인 것이 아닙니다.

## t4 — fixture
- "배송 완료된 주문"을 화면으로 만들려면 로그인 → 담기 → 주문 → 결제 → (관리자) 출고 → 배송 완료까지 필요합니다. fixture는 이를 한 번의 API 호출로 줄이고, 테스트는 **검증하고 싶은 화면 하나**(환불)에 집중합니다.
- 테스트가 만든 데이터의 `id`를 직접 쓰므로 실행 순서나 반복에 영향을 받지 않습니다. 시드 주문 번호를 가정한 테스트는 두 번째 실행에서 깨집니다.
- 경계 상황(7일 경과)은 시간을 흘려보내는 대신 `deliveredHoursAgo`로 만듭니다.
- 한계: fixture는 앱의 내부 규칙을 우회합니다. 그 규칙(주문 상태 전이 등) 자체는 API·단위 테스트로 따로 검증하고, 화면 테스트는 화면에 집중하세요.
