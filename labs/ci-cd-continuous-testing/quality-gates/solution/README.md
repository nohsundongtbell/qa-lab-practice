# 해설 — 워크플로와 품질 게이트

> 스포일러입니다. 직접 풀어 본 뒤에 읽으세요. 이 폴더의 `quality.yml`과 `gate.mjs`가 모범 답안입니다.

## t1 — 워크플로
| 시작 파일의 문제 | 왜 위험한가 | 고친 것 |
|---|---|---|
| `on: [push, pull_request_target]` | `pull_request_target`은 포크의 PR에서도 **저장소의 비밀 값과 쓰기 권한**으로 실행된다. 거기서 PR 코드를 실행하면 비밀 값이 새 나간다. `push`가 모든 브랜치에서 돌면 PR과 같은 실행이 두 번 돈다 | `pull_request` + `push`(main 한정) |
| `permissions` 없음 | 기본 토큰 권한이 넓을 수 있다. 침해되면 피해가 커진다 | `contents: read` |
| `timeout-minutes` 없음 | 멈춘 잡이 기본 6시간 동안 러너를 점유한다 | 15분 |
| `concurrency` 없음 | 같은 브랜치에 연달아 푸시하면 낡은 실행이 계속 돈다 | `cancel-in-progress: true` |
| `actions/checkout@main` | 브랜치는 **언제든 바뀐다**. 오늘 통과한 워크플로가 내일 다른 코드를 실행할 수 있다(공급망) | `@v4`(더 엄격하게는 커밋 SHA) |
| `windows-latest`, `node-version: 20`, `npm install` | 이 저장소의 기준과 다르다. `npm install`은 잠금 파일을 갱신할 수 있어 재현성이 떨어진다 | Ubuntu, Node 24, `npm ci`, `cache: npm` |
| `continue-on-error: true`, `\|\| true` | 실패해도 초록색이다 — **게이트가 아니라 장식**이다 | 제거 |
| `upload-artifact` 없음 | 실패한 뒤에 무엇이 틀렸는지 볼 증거가 없다 | `if: always()`로 보관 |

## t2 — 게이트
- **fail closed**: 지표가 없을 때 통과시키는 게이트는 "지표 수집이 고장 나면 모든 빌드가 통과"하는 게이트입니다. 모르면 막습니다.
- **총 테스트 0개 = 차단**: 테스트 러너가 설정 오류로 아무것도 안 돌려도 `failed`는 비어 있습니다. 실패가 없다는 사실만으로 통과시키면 거짓 성공입니다.
- **경계값**: 정확히 80%, 정확히 2.0포인트, 정확히 1.2배, 격리 마지막 날. 이 네 곳이 부등호 실수가 가장 자주 나는 곳입니다. 부동소수점은 이 숫자들에서는 문제가 없지만, 일반적으로는 정수로 바꿔 비교하는 것이 안전합니다.
- **기준선 대비 하락과 절대 기준을 둘 다 둔 이유**: 절대 기준(80%)만 있으면 95%에서 81%로 떨어져도 통과하고, 기준선 대비만 있으면 천천히 70%까지 내려가도 통과합니다. 서로 다른 실패를 잡습니다.
- **격리(quarantine)로 거짓 경보를 줄이는 법**: 불안정한 테스트 때문에 빌드가 자주 빨개지면 사람들은 빨간색을 무시하기 시작합니다. 격리는 그 테스트를 **기한과 함께** 게이트 밖으로 빼서 신뢰를 지킵니다. 기한이 없는 격리는 영원한 무시가 되므로, 기한이 지나면 다시 막습니다. 격리 중에도 경고를 출력해 잊히지 않게 합니다.
- 한계: 이 게이트는 지표가 정직하다고 가정합니다. 커버리지 숫자를 올리려고 단언 없는 테스트를 쓰면 통과합니다(구조 기반 테스트 랩의 뮤테이션 점수가 이를 보완합니다).
