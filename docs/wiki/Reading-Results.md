# 채점 결과 읽는 법

`npm run check -- <랩>` 는 과제마다 줄을 출력하고, 마지막에 `결과: N/M 과제 통과` 를 보여 줍니다. 종료 코드는 모두 통과면 0, 아니면 1 입니다.

## 공통 원칙
- **정답과 같은지가 아니라 관찰 가능한 결과**로 판정합니다. 같은 결함을 잡는 방법은 여러 가지입니다.
- **실제 값과 정답은 알려 주지 않습니다.** "기대값이 사양과 다릅니다"처럼 무엇이 틀렸는지만 말하고 앱의 실제 값은 숨깁니다. 정답을 알려 주면 채점기가 답안지가 되기 때문입니다. 기대값은 [제품 사양서](https://github.com/nohsundongtbell/qa-lab-practice/blob/HEAD/apps/shop/SPEC.md)로 직접 계산하세요.
- 결함 **번호**(`DF-003` 처럼)는 보여 줄 수 있지만, 그 결함이 **무엇인지**는 알려 주지 않습니다.
- 힌트는 해당할 때만 나옵니다. 그래도 막히면 랩 README 의 "막혔을 때"를 힌트 1 → 힌트 2 순서로 여세요.

## 자주 보는 표시
| 표시 | 뜻 | 할 일 |
|---|---|---|
| `[검출] … → 결함 N개 (DF-…)` | 그 케이스가 결함을 잡았다 | 좋습니다 |
| `[미검출]` | 결함 없는 앱에서도, 결함을 켠 앱에서도 통과 | 결함이 있을 만한 곳(경계, 조합, 상태)을 더 찔러 보세요 |
| `[무효]` | **결함 없는 앱에서도** 기대와 다르다 = 기대값이 사양과 다르다 | 사양서로 기대값을 다시 계산 |
| `[오류]` | 형식이 틀려 실행하지 못했다 | 몇 번째 줄·무엇이 문제인지 메시지를 보세요 |
| `[처치]` / `[생존]` | 고장 낸 코드(뮤턴트)를 내 테스트가 잡았다 / 못 잡았다 | 생존한 함수에서 검증하지 않은 동작을 찾기 |
| `[맞음]` / `[다름]` | 답안 파일의 질문별 정답 여부 (정답은 비공개) | |
| `[통과]` / `[실패]` + 조건 | UI·부하 랩: 그 조건(화면 변형, 지연, 반복)에서 통과했는지 | 실패한 조건을 직접 재현 |
| `요소를 기다리다 시간 초과` | UI 테스트가 요소를 못 찾았거나 원하는 상태가 되지 않았다 | 로케이터·대기 방식 점검 |
| `[너무 느슨함]` / `[너무 엄격함]` | CI/CD 게이트가 막아야 할 것을 통과시켰다 / 통과시킬 것을 막았다 | 경계값 부등호 확인 |

## 채점 중에 일어나는 일
- 많은 랩이 채점할 때 **앱의 DB 를 초기화**합니다(README 에 적혀 있음). 직접 만들어 둔 데이터가 사라질 수 있습니다.
- 채점기는 결함을 **요청 헤더로 직접 켜고 끕니다.** 그래서 내가 어떤 프로필로 앱을 띄웠든 결과가 같습니다. 프로필이 다르면 `[주의]` 가 나오지만 채점은 그대로 진행됩니다.
- 채점기는 항상 원본 도우미 파일(`starter/support/` 등)을 씁니다. 작업 폴더의 도우미를 고쳐도 채점에는 영향이 없습니다.
