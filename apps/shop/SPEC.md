# QA 숍 제품 사양서 (SPEC)

> 이 문서는 실습 대상 앱 "QA 숍"의 **요구사항 명세**다. 테스트를 설계할 때 기대 결과의 근거(오라클)로 쓴다.
> 앱에는 실습을 위해 일부러 넣은 결함이 있을 수 있다. **이 문서와 앱의 동작이 다르면, 이 문서가 맞다.**
> API 형식(요청·응답 필드)은 [`api/openapi.yaml`](api/openapi.yaml)을 따른다.

버전: 1.1 · 통화: 대한민국 원(KRW, 정수) · 시간대: 한국 표준시(KST, UTC+09:00, 일광 절약 시간 없음)

## 1. 회원

### 1.1 가입 (`POST /api/members`)
| 항목 | 규칙 |
|---|---|
| 이름 `name` | 앞뒤 공백을 제거한 뒤 **2자 이상 20자 이하**. 글자 수는 사람이 보는 글자 단위로 센다(한글 1글자 = 1자). 한글·영문·공백만 허용 |
| 이메일 `email` | `로컬@도메인` 형식, 대소문자 구분 없이 유일. 저장할 때 소문자로 바꾼다 |
| 비밀번호 `password` | 8자 이상 64자 이하 |
| 주소 `zipcode` | 숫자 5자리 |
| 결과 | 성공 시 `201`, 등급은 `NORMAL`, 누적 구매액 0원. 규칙 위반은 `400 VALIDATION_ERROR`, 이메일 중복은 `409 EMAIL_TAKEN` |

### 1.2 로그인 (`POST /api/auth/login`)
이메일·비밀번호가 맞으면 `200`과 토큰을 준다. 이후 요청은 `Authorization: Bearer <token>` 헤더를 붙인다. 틀리면 `401 INVALID_CREDENTIALS`.

### 1.3 회원 등급
누적 구매액(배송 완료 `DELIVERED` 주문의 결제 금액 합)에 따라 정한다.

| 등급 | 누적 구매액 | 상품 할인율 |
|---|---|---|
| `NORMAL` | 0원 이상 100,000원 미만 | 0% |
| `SILVER` | 100,000원 이상 500,000원 미만 | 1% |
| `GOLD` | 500,000원 이상 1,000,000원 미만 | 3% |
| `VIP` | 1,000,000원 이상 | 5% |

- 누적 구매액이 음수인 입력은 유효하지 않다(`400`).
- 등급 판정만 따로 확인하는 API: `GET /api/grades/evaluate?totalSpent=<원>`

## 2. 상품과 장바구니
- 상품은 `id`, 이름, 가격(원, 1 이상 정수), 재고(0 이상 정수)를 가진다.
- 장바구니 한 줄의 수량은 **1개 이상 99개 이하**다. 범위를 벗어나면 `400 VALIDATION_ERROR`.
- 수량은 재고를 넘을 수 없다(`409 OUT_OF_STOCK`).
- 같은 상품을 다시 담으면 수량을 **바꾼다**(더하지 않는다). `PUT /api/cart/items/{productId}`

---

## 3. 금액 계산
주문 금액은 다음 순서로 계산한다. 모든 할인은 **원 단위 미만을 버린다**(내림).

1. **상품 금액** `subtotal` = Σ(가격 × 수량)
2. **등급 할인** `gradeDiscount` = ⌊`subtotal` × 등급 할인율⌋
3. **쿠폰 할인** `couponDiscount` = 쿠폰 규칙(§4)에 따라 **`subtotal` 기준**으로 계산
4. **총 할인** = `gradeDiscount` + `couponDiscount`. 단, `subtotal`을 넘을 수 없다
5. **배송비** `shippingFee` (§5) — 무료 배송 기준은 **할인 후 금액**(`subtotal` − 총 할인)으로 판단
6. **결제 금액** `total` = `subtotal` − 총 할인 + `shippingFee`

금액 미리보기 API: `POST /api/quote` (주문을 만들지 않고 계산 결과만 돌려준다. 로그인한 회원의 등급을 쓴다)

---

## 4. 쿠폰
| 항목 | 규칙 |
|---|---|
| 정액 쿠폰 `FIXED` | `amount`원 할인 |
| 정률 쿠폰 `PERCENT` | ⌊`subtotal` × `rate`%⌋ 할인. 단 **최대 할인액 `maxDiscount`원을 넘지 않는다** |
| 최소 주문 금액 `minOrderAmount` | **`subtotal`(할인 전 상품 금액)**이 이 값 **이상**이어야 쓸 수 있다 |
| 유효 기간 | `validFrom` 00:00:00 ~ `validUntil` 23:59:59 (KST, 양 끝 포함) |
| 사용 횟수 | 회원에게 발급된 쿠폰 1장은 **한 번만** 쓸 수 있다. 주문 한 건에 쿠폰은 최대 1장 |
| 복원 | 쿠폰을 쓴 주문이 **취소**(`CANCELLED`)되면 쿠폰은 다시 쓸 수 있게 된다. 환불(`REFUNDED`)은 복원하지 않는다 |

쓸 수 없는 쿠폰을 지정하면 주문·미리보기 모두 `422 COUPON_NOT_APPLICABLE`과 사유(`reason`)를 돌려준다.
사유 값: `NOT_FOUND`, `NOT_OWNED`, `ALREADY_USED`, `EXPIRED`, `NOT_STARTED`, `MIN_ORDER_NOT_MET`.

## 7. 주문

### 7.1 상태와 전이
```
PENDING ──pay──▶ PAID ──ship──▶ SHIPPED ──deliver──▶ DELIVERED ──refund──▶ REFUNDED
   │               │
   └──cancel──▶ CANCELLED ◀──cancel──┘
```
| 동작 | API | 허용되는 현재 상태 | 결과 상태 |
|---|---|---|---|
| 주문 생성 | `POST /api/orders` | (장바구니) | `PENDING` |
| 결제 | `POST /api/orders/{id}/pay` | `PENDING` | `PAID` |
| 취소 | `POST /api/orders/{id}/cancel` | `PENDING`, `PAID` | `CANCELLED` |
| 출고 (관리자) | `POST /api/admin/orders/{id}/ship` | `PAID` | `SHIPPED` |
| 배송 완료 (관리자) | `POST /api/admin/orders/{id}/deliver` | `SHIPPED` | `DELIVERED` |
| 환불 | `POST /api/orders/{id}/refund` | `DELIVERED`, 배송 완료 후 **7일 이내**(배송 완료 시각 + 168시간까지) | `REFUNDED` |

- 허용되지 않은 전이는 `409 INVALID_STATE_TRANSITION`이며 주문은 바뀌지 않는다.
- 다른 회원의 주문에 접근하면 `404 NOT_FOUND`.

### 7.2 주문 생성
- 장바구니가 비어 있으면 `400 CART_EMPTY`.
- 주문을 만들 때 각 상품의 **재고를 수량만큼 줄이고**, 쿠폰을 **사용 처리**하며, 장바구니를 비운다.
- 주문 시점의 상품 가격·금액 계산 결과를 주문에 저장한다. 이후 상품 가격이 바뀌어도 주문 금액은 바뀌지 않는다.
- 저장된 결제 금액 `total`은 언제나 §3 계산 결과와 같아야 한다(주문 상세 `GET /api/orders/{id}`).

### 7.3 결제
- 가짜 결제다. 카드 번호 `4000-0000-0000-0002`는 **승인 거절**(`402 PAYMENT_DECLINED`, 주문은 `PENDING` 유지), 그 밖의 16자리 번호는 승인된다.
- 결제에 성공하면 결제 시각과 배송 예정일(§6)을 주문에 저장한다.

### 7.4 취소와 환불
- 취소하면 주문 수량만큼 **재고를 되돌리고**, 쿠폰을 복원한다(§4).
- 환불하면 재고를 되돌린다. 쿠폰은 복원하지 않는다. 환불된 주문은 누적 구매액에서 빠진다.

## 8. 오류 응답 형식
모든 오류는 다음 형식이다.
```json
{ "code": "VALIDATION_ERROR", "message": "사람이 읽을 수 있는 한국어 설명", "details": {} }
```
요청마다 응답 헤더 `X-Request-Id`가 붙는다. 같은 값이 서버 로그의 `reqId`에 남는다.

- 각 API가 돌려줄 수 있는 상태 코드는 `api/openapi.yaml`에 적힌 것뿐이다. 요청이 잘못된 경우는 `4xx`이며, `5xx`는 서버 내부 오류일 때만 쓴다.
- 성공 응답의 필드와 타입도 `api/openapi.yaml`의 스키마를 따른다(필수 필드 누락, 타입·열거값 불일치는 결함이다).

## 9. 성능 목표 (로컬 실습 기준)
내 컴퓨터에서 대상 앱만 띄우고, **동시 사용자 10명**이 계속 요청할 때의 목표다. 오류율은 모든 API에서 1% 미만이어야 한다.

| API | 조건 | 응답 시간 p95 |
|---|---|---|
| `GET /api/products` | | 100ms 이하 |
| `GET /api/orders` | 주문이 10건 이하인 회원 | 200ms 이하 |
| `POST /api/quote` | 상품 3종 이하 | 100ms 이하 |

- 응답 시간은 요청을 보낸 뒤 응답을 다 받을 때까지의 시간이다.
- 이 수치는 실습용 기준이다. 컴퓨터 성능에 따라 결과가 다를 수 있으니, 결함 없는 프로필(`none`)에서 먼저 기준선을 재고 비교한다.

## 10. 화면 접근성 (웹)
키보드만 쓰는 사용자와 화면 낭독기 사용자도 모든 화면 기능을 쓸 수 있어야 한다. 아래는 이 서비스의 화면 요구사항이다.

| 번호 | 요구사항 |
|---|---|
| 10.1 | 내용이 있는 이미지에는 그 내용을 전하는 대체 텍스트(`alt`)가 있다. 장식용 이미지는 빈 대체 텍스트(`alt=""`)를 쓴다. |
| 10.2 | 모든 입력 칸에는 보이는 레이블이 있고, 레이블이 입력 칸과 프로그램으로 연결되어 있다(`<label>` 등). |
| 10.3 | 글자와 배경의 명도 대비는 4.5:1 이상이다(18pt 이상 또는 14pt 이상 굵은 글자는 3:1 이상). |
| 10.4 | 모든 버튼과 링크에는 접근 가능한 이름이 있다. 아이콘만 있는 버튼은 `aria-label` 등으로 이름을 준다. |
| 10.5 | 제목(`h1`~`h6`)은 수준을 건너뛰지 않는다. 화면마다 `h1` 은 하나이고, 그 아래 목록 항목의 제목은 `h2` 다. |
| 10.6 | 마우스로 할 수 있는 모든 동작은 키보드(Tab·Shift+Tab·Enter·Space)로도 할 수 있다. |
| 10.7 | 키보드 초점이 간 요소는 눈에 보이게 표시된다. |
| 10.8 | 화면 맨 위의 실습 안내 띠(“실습용 서비스입니다…”)는 모든 화면에 고정으로 붙는 안내로, 랜드마크(`header`·`main`·`nav`) 밖에 두는 것을 허용한다. |

- 화면 변형(`UI_VARIANT`)은 환경 조건이다. 접근성 요구사항은 기본 화면(`v1`) 기준으로 확인한다.
